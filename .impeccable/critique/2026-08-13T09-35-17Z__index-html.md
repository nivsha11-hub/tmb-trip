## Design Specificity Verdict

**Authored, with a category-interchangeable admin tail.**

The map half could not be swapped into another product: triple-stroke route rendering (black shadow 14px / white casing 10px / per-day color 6px, 1797-1810) is a real cartographic decision because thin lines vanish against Esri imagery; terrain at exaggeration 1.5 with a hand-tuned sky/fog palette (1774-1782); `clip-path` triangles for cols vs circles for refuges (1867); 22 named passes with elevations including `Fenêtre d'Arpette ⭐ point le plus haut` (1183). Brass on near-black at radius 2px with an uppercase Latin wordmark inside a Hebrew RTL shell.

The admin panel is the opposite: `.add-form` + `.list-item` + `.li-actions` + a `.stat-card` grid. Strip the Hebrew and it is any CRUD dashboard of the last decade. Operate mode permits that familiarity, but it means the product's character stops at the panel boundary.

The biggest authorship gap: **nothing in the interface knows what day it is.** There is a countdown but no "today" — no current-day highlight, no auto-selected day, no "next hut" card. For a product whose stated success condition is "on any evening of the trip, any member can open the app and get the next day's route," the absence of a *today* is the structural miss.

**Deterministic scan:** 3 detector findings. `[side-tab]` at 2108 fires on `border-right:3px solid ${color}30` — in RTL that IS the leading edge, so the rule's pattern genuinely matches, but the stripe is a per-day data color at 19% alpha, not decoration. The real defect the finding exposes is adjacent: three border declarations on two opposite edges of one card (94 `border-left` accent for `.on`, 383 `border-left` divider at mobile, 2108 inline `border-right` day color). The two `[layout-transition]` findings (155, 258) are false positives — 3px-tall determinate progress fills inside `overflow:hidden` parents where width is the semantic quantity.

## Overall Impression

The engineering discipline is well above the design discipline. The write path is genuinely trustworthy — every mutation waits for Postgres and rolls back in memory before any success toast (2682, 2697, 2946, 2968, 3115), with a realtime echo guard comparing `updated_at` to `_lastLocalWriteAt` (1334, 1668) so your own write cannot clobber an in-flight edit. Very few apps this size get that right.

What is missing is the last mile to the user. The itinerary is already cached in `localStorage` before auth runs (1276, called at 3225), yet a weak signal produces a login box instead of the trip. The mobile media query deletes the two facts the product exists to deliver. And the one place real money is at stake reaches the user only because a note happens to contain an emoji.

The single biggest opportunity: make the app know what day it is, and let it render from cache.

## What's Working

1. **The route rendering is a real cartographic solution, not a default.** Three stacked line layers per day (1797-1810) because a 6px colored line alone is illegible over aerial imagery; `terrarium` DEM at 1.5x exaggeration (1769-1774); per-day `SEGMENT_COLORS` (1190); triangles-for-cols vs circles-for-refuges (1867); 22 hand-entered passes with elevations (1164-1187). No template supplies this.
2. **The write path honors "the database is the truth" literally.** `saveState` returns a boolean (1337-1375); every caller restores the previous in-memory value and re-caches on failure, and toasts success only when `ok`.
3. **Auth error copy is better than most funded products ship.** `loginErrorMessage` (1437-1448) maps `invalid_credentials`, `email_not_confirmed`, `over_request_rate_limit` and `user_banned` to specific Hebrew with a specific next action; the confirmation branch flips the form back to login, names the address, colors it `--ok` for 12s (1478-1488); a 15s anti-spinner net (3278-3285).

## Priority Issues

### [P0] The auth gate withholds a complete cached itinerary when the network is weak

`#app` only becomes visible via `startApp()`, reachable only through `loadProfileAndStart()`, which requires a live Supabase token (1567-1568). But `loadStateFromLocal()` (1276, called at 3225) has already populated `S.huts`, `S.segments` and `S.trip` from `localStorage['tmb_v4']` before any auth. If Supabase is unreachable the 15s net shows `החיבור לשרת איטי או נכשל` and the user gets a login box — while the full itinerary, every phone number and booking status sits two function calls away. Combined with the 30-minute auto-logout (3288) which fires with no warning and `signOut`s 1.5s after a toast (3295-3297), a member checking the app twice in a refuge with no data gets nothing the second time.

This is the exact scenario PRODUCT.md names: "on any evening of the trip, any member can open the app on a phone and get the next day's route... without asking anyone" and "It has to work on a phone with a bad signal."

**Fix:** when `loadProfileAndStart` fails on *network* (as distinct from bad credentials) and a cached `tmb_v4` plus cached `display_name`/`role` exist, boot into read-only offline mode: map + overview from cache, admin nav hidden, persistent banner `מצב לא מקוון · הנתונים מ-<timestamp>`. Store `updated_at` in `cacheLocal()` (1326) so the timestamp is honest. Make the inactivity timeout a soft lock (re-show from cache, require auth only to write) rather than a full sign-out.
**Command:** `/impeccable harden`

### [P1] Mobile hides exactly the facts the product exists to deliver, and the floating hamburger sits on what's left

(a) In `@media(max-width:768px)`: `.day-hut{display:none}` (384) removes the hut name **and its booking status badge** from every day card; `.trip-meta{display:none}` (380) removes group and dates; `.map-legend{display:none}` (388) removes the day-to-color key while the route stays colored per day. On a phone the day strip shows only `יום 5 · 24 ק"מ · +1750מ' · קשה מאוד`. Answering "where do we sleep and is it booked" now costs: tap card → 1000ms `flyTo` (2057) → find marker → tap → read popup.

(b) `.hamburger` is `position:fixed; top:12px; right:12px` at 44x44 (363-368) while `.topbar{display:none}` (360), so every panel starts at y=0 under it. In RTL the right edge is the leading edge — precisely where each panel puts its most important element. Three collisions: `.sidebar-head` h2 (378, at the right end of the now-horizontal map sidebar, which is first in DOM so it sits at the top), `.info-tabs` sticky `top:0` with `סקירה` first (394), and `#admin-mobile-title` at the right of `.admin-mobile-bar` (281).

**Fix:** keep `.day-hut` visible on mobile — it is the highest-value 20px on the screen; drop `.day-stats` instead if space is tight. Restore the legend as a collapsed chip. Give the hamburger reserved space (`padding-inline-start:56px` on those three, RTL-safe) or move it into per-panel bars.
**Command:** `/impeccable adapt`

### [P1] "Is it booked?" is answered three different ways, and the money warning rides on an emoji

The same `hut.status` renders three ways: text badge where `.status-badge.none` is `--danger` red (104); legend where `.legend-dot.none` is `--muted` grey with transparent fill (120); and on the marker itself **no encoding at all** — only `.hut-marker-el.booked` and `.pending` get a ring (136-137), so "not booked" is meaning-by-absence layered on meaning-by-color-alone. The one consequential detail, ~35 EUR owed at Elisabetta, surfaces only via `hut.notes.includes('⚠️')` (2002, 2269) — delete the emoji while editing the note and the payment warning silently vanishes from both the map popup and the overview. It then renders in `--muted2` (2314), the lowest-contrast token in the palette at 1.96:1.

**Fix:** add `.hut-marker-el.none .hut-marker-circle{box-shadow:0 0 0 2px var(--danger)}` and reconcile `.legend-dot.none` to `--danger`; add a glyph inside the ring so status survives greyscale and daylight. Replace `.includes('⚠️')` with a real `hut.warning` / `amountDue` field so an admin editing a note cannot delete the reminder. Move the notes block off `--muted2`.
**Command:** `/impeccable clarify`

### [P1] The admin panel cannot maintain the data the rest of the app displays, and one path fails silently

- **Silent write failure.** `renderEquipPanel` disables checkboxes only when `!isOwn && !isAdmin()` (2409), so an admin sees another member's checkboxes enabled. `toggleEquip` permits the mutation (2433), updates `equipProgress`, re-strikes the label and re-renders progress — then skips the save because of `if (uid === sbUser?.id)` (2450), and `saveEquipProgress` only ever builds rows for `sbUser.id` (2463, 2474). Full success feedback for a write that never happens, silently reverted on the next realtime render.
- **No edit path.** The section header reads `הוסף / ערוך מקטע` (697) but the only controls are add, a status select, and delete (2717-2724, 2987-2989). Fixing a typo means delete and re-add, losing status.
- **The form cannot produce the fields the map renders.** `addHut` (2647-2658) writes no `date`, no `website`, and hard-codes `type:'hut'` — yet the popup renders a date chip from `hut.date` (1999) and a booking link from `hut.website` (1986), and `renderDaysList` selects on `h.type!=='town'` (2104). Every hut added through the panel is permanently missing its booking link. This violates Product Principle 2: the only way to give a hut a URL today is to edit `DEFAULT_HUTS` in source.
- `h-day min="1"` (674) makes the seeded day-0 arrival hut (803) unrepresentable.

**Fix:** decide the admin's intent about others' gear and make the UI say it — either disable whenever `!isOwn` (one line at 2409, matching the honest `צפייה בלבד` badge at 2392) or pass `uid` through `saveEquipProgress` and let RLS reject loudly. Add `date`, `website`, `type` to the hut form; set `min="0"`. Implement edit (prefill the form, swap the button) or retitle the section so the label stops promising it.
**Command:** `/impeccable harden`

### [P1] Daylight legibility fails the product's own bar, and pinch-zoom is disabled

Exact ratios: `--muted` #6b6660 = 3.44 / 3.18 / 2.93 on bg / surface / surface2; `--muted2` #4a4745 = 2.12 / 1.96 / 1.81. `--muted` carries 31+ declarations, every one at 10-13px normal weight, so the 3:1 large-text allowance never applies. `--muted2` carries `.member-perms` 10px (2.12), `.own-only` 11px on surface2 (1.81) and the trip-notes block at 12px (2.12).

Two more contrast layers the audit surfaced only via measurement:
- **`#fff` on the day/avatar palette fails almost everywhere.** `.hut-marker-circle` (14px/800), `.member-avatar` (14px/700), `.ov-hut-day` and `.ov-group-avatar` (11px/700) all paint white text on `SEGMENT_COLORS`/`AVATAR_COLORS` fills. 8 of 9 fills fail 4.5:1; three fail even 3:1 — #e9c46a = 1.67, #f4a261 = 2.06, #00bbf9 = 2.22.
- **Status pills fail on their own washes.** `--danger` on `--danger-bg` over surface = 4.14, over surface2 = 3.79; `--ok` on `--ok-bg` over surface2 = 4.34. `.status-badge` is 10px.

And line 5 disables the workaround twice: `maximum-scale=1.0, user-scalable=no`. WCAG 1.4.4. It buys nothing — mobile inputs are already 16px (446) so there is no zoom-on-focus to prevent.

**Fix:** delete both zoom blocks from line 5. Lift `--muted` to ~#8f8a82 (4.6:1) and `--muted2` to ~#787269, restricting the latter to genuinely decorative use. Move the trip-notes block to `--text`. For the palette circles, either darken the three light day colors or drop white text for `#0c0c0c` on the light fills. Raise 10px labels to 11-12px and `.hut-marker-label` from 9px to 11px.
**Command:** `/impeccable typeset`

### [P1] The hut marker's day number is invisible

`<div class="hut-marker-circle" style="background:${dayColor};color:${dayColor}">${dayLabel}</div>` (1981). `.hut-marker-circle` sets `color:#fff` (133) for the digit; the inline style overrides it, painting the digit in the background color. The inline color exists so `::after` can pull `currentColor` for the pointer triangle (134). Result: 9 markers with no readable day number. Note the fix interacts with the contrast finding above — restoring `#fff` on #e9c46a still yields 1.67:1.

**Fix:** move the triangle color to its own custom property (`--tip:${dayColor}`) and keep `color` for the digit.
**Command:** `/impeccable polish`

## Questions to Consider

1. **Why does the app not know what day it is?** What if opening it on the trail landed on today's day card, pre-selected, with tomorrow's hut and its status as the single largest element on screen — and the map, stats and gear list all became secondary to that one card?
2. **What is a booking status worth without evidence?** `booked` is currently one word an admin typed. Would the group argue less if it carried its receipt — who confirmed it, when, the reference, what is still owed?
3. **If the itinerary is already on the phone, why does the network decide whether the user can see it?** What would a cache-first version look like, with auth required only for writes and an honest "last updated" on screen?
4. **Should the equipment checklist and the trip overview be one nav item?** One is a personal 38-tap pre-trip chore, the other a shared read-only trail reference. The desktop topbar already calls it `סקירה` (535) while mobile calls it `סקירה וציוד` (521) — the ambivalence is already in the code.
5. **What would a confident version of the admin panel look like?** What if editing a hut happened on the map — click the marker, edit in place, status as a three-way segmented control — and the panel shrank to members and trip details?
